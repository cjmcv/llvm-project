# NT 中文注释 Skill

按用户长期形成的偏好,为源码文件添加以 `// <NT>` 起头的中文注释。所有函数级注释只用一行 `<NT>` 起始,后续行不再重复;文件级注释用三段式结构。

## 何时使用

- 用户说: "加 NT 注释"、"中文注释"、"用 NT 风格"、"以 <NT> 开头"
- 用户要求: 给某个 C/C++/LLVM 源文件加注释
- 用户强调: 中文、一句话、关键字标记

## 何时不要使用

- 用户只想要英文注释 → 不触发
- 用户要生成文档 (markdown / rst) → 不触发
- 用户只问代码理解、不需要写注释 → 不触发

## 注释标记规范

```
每段注释以 // <NT> 开头(只写一次,在第一行)
后续行不再重复 <NT>
函数级注释写在函数定义之前一行
文件级注释写在 license 头之后、#include 之前
类成员之间用空行隔开

**函数级 <NT> 首行必须用「具体角色标签:」开头** (3-15 字, 像标题),
不能写泛词. 例如:
  ✅ // <NT> 反汇编器工厂入口:
  ✅ // <NT> Zicfilp 对齐 call 发射:
  ✅ // <NT> MI emit 分派中心 (每条 MachineInstr 的总入口):
  ✅ // <NT> 立即数加载的统一入口:
  ❌ // <NT> 关键函数说明:           <- 泛词, 不允许
  ❌ // <NT> 注释:
  ❌ // <NT> 这个函数:
```

**文件级三段首行固定为**:
  `// <NT> 文件简介:`
  `// <NT> 关键函数串联 (...):`
  `// <NT> 总结:`

## 注释内容三要素 (必须详细)

**核心原则: 少而精.** 只挑关键函数加注释, 但每条注释必须写得**详细**,
把函数职责、调用上下文、关键机制讲透; 不要为了凑数给次要函数加一行
简短的注释, 也不要为了行数限制把一个关键函数的注释挤成一行.

每个函数级 `<NT>` 注释必须详细覆盖:

```
① 函数职责: 这个函数干什么, 在哪条流水线上
② 调用上下文: 谁会调用它 (调用方 + 调用链), 上游输入是什么, 下游输出到哪里
③ 关键机制: 为什么这么写 / 关键算法 / 引用的 TableGen 产物 / 配对函数名
④ 副作用或陷阱: 改了哪些全局状态 / 在哪些 RV32E / RVV / 厂商扩展下行为不同
```

**详细注释示例**:

```
// <NT> 立即数加载的统一入口: 给定目标寄存器和 64 位常数, 自动选择最短的
//   LUI/ADDI/SLLI 序列 (1-8 条指令). 拆分算法见 RISCVMatInt::splitImm,
//   会根据常数大小动态选 1 条 (lui/addi) 或最多 8 条 (lui + 4×(slli+addi))
//   的最短序列. 是 RV64 上 li 伪指令的最终落地; 被 processInstruction
//   在处理 PseudoLI/PseudoLA 时调用. 注意负数需要 12 位加立即数区间
//   偏移, 算法里有 special-case.
```

每条注释 5-10 行, 内容详实, 能让读者不需要读源码也能知道函数干什么.

## 行宽与换行规范 (重要)

**核心原则: 美观优先, 长度其次.**

```
- 不要为了"填满行"而硬塞一长行
- 不要为了"短行对齐"而把一句完整的话拆成 3-5 行碎片
- 结构分层 + 缩进 + 视觉对齐 > 单行字符数
- LLVM 代码本身后端行宽常达 150-200 字符, 注释 60-100 字符完全可接受
```

**好的风格** (短行 + 缩进 + 分层):

```
// <NT> 总结:
//   本文件是 RISC-V 后端汇编侧的总控, 三大职责:
//     1) 助记符 -> MCInst 的匹配与编码 (委托给 TableGen 生成的 MatchInstructionImpl)
//     2) 伪指令 (la/li/call/tail/sext/TLS 等) -> 真实指令序列的展开
//     3) 汇编级指令 (.insn/.option/.attribute) 与错误诊断
//   对学习者而言, 推荐的阅读顺序是: 先看 matchAndEmitInstruction / parseInstruction /
//   processInstruction 抓住主流程, 再按需跳到 emitLoadImm / emitLoadAddress /
//   emitPseudoExtend 看具体伪指令展开, 最后看 parseDirective* 理解汇编指令支持.
//   所有函数级的中文注释均以 "// <NT>" 开头, 方便搜索定位.
```

视觉上断行清晰, 读者扫一眼就能抓住结构.

**差的风格** (硬塞长行):

```
// <NT> 总结: 本文件是 RISC-V 后端汇编侧的总控, 三大职责: (1) 助记符 -> MCInst 的匹配与编码 (委托给 TableGen 生成的 MatchInstructionImpl);
// (2) 伪指令 (la/li/call/tail/sext/TLS 等) -> 真实指令序列的展开; (3) 汇编级指令 (.insn/.option/.attribute) 与错误诊断.
// 对学习者而言, 推荐的阅读顺序是: 先看 matchAndEmitInstruction / parseInstruction / processInstruction 抓住主流程, 再按需跳到 emitLoadImm / emitLoadAddress /
// emitPseudoExtend 看具体伪指令展开, 最后看 parseDirective* 理解汇编指令支持. 所有函数级的中文注释均以 "// <NT>" 开头, 方便搜索定位.
```

单调的长行, 读者视线要左右扫, 难以抓住层次.

**函数级注释细则**:
- 单行能讲清就用单行 (一行 ≈ 50-80 字符为佳, 不超 120 字符)
- 多行注释: 后续行不强制与第一行等长, 但优先在标点 (，。：；/ ; , :) 后断行
- 不在英文单词中间断开
- 总行数 ≤ 6 行; 超过则内容没收敛
- 函数级注释优先短小精悍, 文件级注释优先结构清晰

## 语言与风格

```
语言: 简体中文
技术词: 英文术语保留 (MCInst / Pat / Predicate / Relax / TLS / VTYPE / Subtarget 等)
长度: 函数级单行 ≤100 字,复杂函数 2-3 行
语气: 陈述式,不要"我们""你""应该"等
格式: 用半角标点 + 半角逗号,中文之间不断行
```

## 函数选优先级 (少而精原则)

**核心: 宁可少, 不可滥.** 一个 4700 行的文件, 加 5-10 条**详细**注释
比加 50 条一行简短注释更有价值. 优先选择"能串起整个流程脉络"的节点.

```
重点(必注, 每条详细):
  - 主入口 / 顶层调度 (parseInstruction, getInstruction, ...): 1-2 条
  - 关键分发节点 (processInstruction, matchAndEmitInstruction, ...): 1 条
  - 关键模板 / 基类 (DecodeSimpleRegisterClass, RVInstR, ...): 1 条
  - 关键算法节点 (emitLoadImm, decodeInstruction, ...): 1 条

跳过(一律不注):
  - 与主流程无关的纯分支辅助 (decodeImmThreeOperand, generateVTypeError, ...)
  - 调试用辅助函数
  - 第三方兼容代码块
  - 简单 one-liner (DecodeGPRX1RegisterClass 等)
  - 即使是重点函数, 如果只是 trivially forward 其它函数, 也跳过
```

**目标密度**: 1000 行文件加 5-10 条, 5000 行文件加 15-25 条.
**反模式**: 1000 行文件加 30+ 条 → 99% 是次要注释, 应该删掉.

## 文件级注释结构 (三段式, 必含三节)

文件级 `<NT>` 注释**必须**三段式, 三节缺一不可, 不可只写"文件简介"一段:

```
//===-- 文件名 - 简要说明 -===//
// ... license / SPDX ...
//===----------------------------------------------------------------------===//
//
// <NT> 文件简介:
//   定位 (LLVM 哪一层)、输入输出、上游调用方、下游接收方.
//
// <NT> 关键函数串联 (主流程):
//   顶层入口:
//     foo()          描述
//       └─> bar()    描述
//             ├─ 路径 A
//             └─ 路径 B
//   分类 / 子模块:
//     baz()          描述
//
// <NT> 总结:
//   三大职责 + 推荐阅读顺序 + 注释标记说明.
//
//===----------------------------------------------------------------------===//
```

**对每个文件都必须写这三节**, 即使文件很小 (如 RISCVMatInt.cpp).
跳过其中任何一节都是错误.

关键函数串联节可以简化 (例如一个文件只有一个主入口, 就列这一条),
但不能整节删除. 总结节要点出文件的核心职责, 不能写成"本文件实现了 X 类"一句话.



## ASCII 调用图约定

```
└─>   串接调用
├─    并列分支一
└─    并列分支二
│     竖线连接
```

主流程用树形,分类清单用平铺。

## 工作流程

1. **读文件总览**: `wc -l`、扫函数签名、识别 license 头位置
2. **规划函数清单**: 列出"重点函数 / 跳过函数",用户可见地展示
3. **写文件级注释**: 三段式,插在 license 之后
4. **批量插函数级注释**: 按行号倒序 / 自下而上,避免行号漂移
5. **验证**: `grep -c '^// <NT>' FILE` 检查数量,展示列表

## 编辑策略 (硬性规则)

```
1. 不删除原文, 只增不减: 不删除 / 不改写文件里原有任何注释、license、
   空行、include 顺序; 只在适当位置插入 <NT> 注释块.
2. 不截断函数: <NT> 注释块必须完整地写在函数定义之前, 中间不能被
   函数签名打断. 错误示例:
     template <unsigned N>
     // <NT> ...   <-- 注释卡在函数签名中间
     static int foo() { ... }
   正确写法: 注释完整地写在 template 行之前:
     // <NT> ...
     template <unsigned N>
     static int foo() { ... }
3. 不用 Edit 工具的"删除"语义: 永远用 Edit 工具的"插入"形态 (把
   old_string + new_string 中 new_string 在 old_string 之前插入 <NT> 注释),
   绝不删除任何现有行.
4. 一次只插一条 <NT> 注释, 避免大段替换失败.
5. 函数级 <NT> 不带空行夹在函数定义前.
```

## 编辑反例 (不要这样写)

```
// ❌ 注释截断了 template 行
template <unsigned N>
// <NT> foo 函数
static int foo() { ... }

// ❌ 删除了原 license 注释
// (删除了 "// Part of the LLVM Project...")
// <NT> 自定义文件头

// ❌ 把 <NT> 注释和原注释合并
// <NT> 这个函数是 foo + 原作者注释
static int foo() { ... }
```

## 输出与对话

- 完成后给出"插入了 N 条 `<NT>` 注释"的总结
- 列出跳过的函数及原因
- 不要把注释内容复制到对话里(用户已经能从 grep 看到)
- 不需要生成任何 markdown 文档(用户偏好直接改源文件)

## 反例(不要这样写)

```cpp
// <NT> 这个函数用来解析立即数
// <NT> 它会被 parseInstruction 调用
// <NT> 输入是一个字符串
int foo(...) { ... }     // ❌ 每行都加了 <NT>

// <NT> foo
int foo(...) { ... }     // ❌ 没讲做什么

// 我们建议你应该在此处添加立即数解析逻辑
int foo(...) { ... }     // ❌ 用"我们""应该"
```
